# XML Web Services API references index

Extraction of the **Sage Intacct XML Web Services API** ("XML API", DTD 3.0) from Sage's developer portal and
request schema, plus an object-definition snapshot of a clean developer company. Read `api-basics.md` first for the
protocol, then open only the section file or snapshot range the request needs. `objects/`, `objects.md`,
`functions.md` and `snapshot/` are generated by the scripts in `scripts/`; the three other files are hand-curated
from the portal's guide pages. Nothing here covers the **REST API**.

## Looking things up

Grep; never read a section file whole (the large ones are 3,000 to 6,000 lines).

| Question | Where |
|---|---|
| Does the object or operation exist, which function does it use, is it legacy | `objects.md`: grep the object (`APBILL`), the page (`Items`), the operation words (`Create Item`) or the function (`create_sotransaction`) |
| Which objects does a page document | the `Objects in examples` column of the table at the top of the section file, or `<object>NAME</object>` in the examples |
| Does a field exist on an object, its data type, read-only flag and valid values, as the API reports them | `snapshot/objects.md` for the object's `File` / `Line` / `Lines`, then that range of `snapshot/fields-NN.md`; grep a bundle for `` `FIELDNAME` `` to find every object carrying it |
| How two objects relate (the `OBJECTPATH` for `query` dot notation, `MANY2ONE` etc.) | the object's relationships table in its `snapshot/fields-NN.md` block |
| The fields of a create or update, which are required, allowed values | the section file: grep `` Function: `create` `` or `` Function: `create_sotransaction` `` under the operation, then the `**Parameters**` tables that follow (`| FIELD | Required | type | description |`); nested objects are introduced by their anchor and name |
| The filter fields and database values of a legacy list (`STATE` codes) | the `` `query` Fields `` table under the page's `readByQuery` operation |
| When a field was added or changed | the `Release history:` table under the operation |
| The exact grammar of a generic function (`query`, `readByQuery`, `read`, `getAPISession`...) and of the request envelope | `functions.md`: `### \`query\``, type `filteroption`, the operator elements |
| Is `verb_object` a real legacy function | the last section of `functions.md` |
| Protocol rule: headers, sessions, errors, paging, dates, limits | `api-basics.md` (sections numbered for citation) |
| OE / Purchasing / Inventory document flow, keys, states, line numbering | `oe-po-inventory.md` |
| The wrong pattern and the rule | `common-mistakes.md` |

## Known limits of these references

- **One snapshot, no release stamp.** The portal states no edition; "verified" is the fetch date. Per-field
  release-history tables are reproduced where the portal has them (most create/update operations).
- **XML API only.** The REST API (GA since 2025 Release 1 per Sage's schema README; new objects ship there) is not
  bundled; answer REST questions with the not-reference-backed caveat and say the skill can be extended.
- **Two sources that answer different questions.** The portal tables (`objects/`) say what a create or update accepts
  and show examples; the snapshot (`snapshot/`) says which fields, values and relationships the API reports. A
  `REQUIRED` of `true` in the snapshot describes the object, not a request (`SODOCUMENT.DOCNO` is required and
  read-only; `ITEM.COST_METHOD` is required there but optional on create). Valid-value lists can be longer in the
  snapshot than in the portal's code tables (`SODOCUMENT.STATE` has four values with no documented `readByQuery`
  character). The snapshot is one clean company on 2026 Release 3 without `docparid`: a client's custom fields,
  user-defined dimensions and transaction-definition fields are not in it.
- **The schema is permissive.** `functions.md` reflects the XSD: it marks `password` and `dtdversion` optional in
  `control` and types most elements as plain text; the portal's rules (`api-basics.md`) win where stricter.
  `consolidatebytier` exists as an element but is not in the schema's `function` choice, so it is not listed.
- **Portal irregularities reproduced as written:** a few parameter tables write `No` instead of `Optional`
  (Inventory Work Queue pages); the work-queue `lookup` examples use mixed-case object names while the tables use
  upper case (the snapshot reports `INVENTORYWQORDER` / `INVENTORYWQDETAIL`); Warehouse Transfers spells `VENDDORID`
  (the snapshot reports `ICTRANSFERITEM.VENDORID`); 39 operations have no `<object>` in their examples (the
  `Object` column of `objects.md` is then empty); some pages label a non-function heading (`Response`) at the same
  level as function names, rendered here as a bold label.
- **No error-code catalogue, no rate-limit figures, no field-level validation messages** beyond the examples the
  guides give (`api-basics.md` § 5, § 10): say so rather than guess.
- **Examples carry the portal's sample data** (vendor IDs, dates, names); none is a real company.
